### Testing TOAST from the project directory

Run the same program that is packaged for tournament directors:

```powershell
.venv\Scripts\python.exe fll-toast.py --tournament-dir tournaments/Dunford --output-dir workspace/toast-test/Dunford
```

The tournament folder supplies the configuration, saved OJS workbooks, and templates.
HTML and logs go to the output folder when `--output-dir` is supplied. Normal validation
and prompts still apply; this does not bypass checks. Save and close the OJS in Excel
first so TOAST reads current calculated scores.

Without these options, TOAST still finds a tournament in the working directory, then
beside the script or executable. Tournament directors can continue running the EXE
inside their tournament folder with no arguments. No separate test build is needed.

Package with `.venv\Scripts\pyinstaller.exe fll-toast.spec`. Distribute the EXE with
the tournament configuration, OJS files, and Jinja templates generated by Maestro.

### TOAST validation and season settings

Set `robot_game_max_score` in the season JSON (currently 530). Maestro copies it to
`INFO.robot_game_max_score` in generated tournament configurations. Older configs
without this field default to 530; update the season setting before future seasons.

TOAST requires integer robot scores from 0 through that maximum, integer rubric
scores from 0 through 4, and GP values of 0, 2, 3, or 4. The existing zero-score
policy is retained. It checks team identities across sheets, saved calculated
scores/ranks, award labels and quotas, and advancement selections. Missing or
duplicate award winners and stale/missing calculations block output. Missing an
alternate is a warning; multiple alternates are an error. Champion's-rank ties
are valid. Robot-game ties affecting award places require resolution.

Both `team_list_D1/D2` and the legacy `div1_list/div2_list` template names work.
Missing template data or collection failures stop generation; both templates are
rendered before either HTML file is written. Failed validation leaves prior HTML
files untouched; they are not results of the failed run.

Each OJS is loaded once per run, with parsed tables shared across validation and
collection. Test with `.venv\Scripts\python.exe -m unittest discover -s tests -v`.
The end-to-end tests use the local scored Dunford fixtures when available.

```bash
# Interactive mode (with prompts and validation summary)

# Verbose/debug mode
```

## Modes

### Quiet Mode (Default)
- Minimal console output
- Logs everything to file
- Always prompts for tournament selection
- Best for regular use

### Interactive Mode (`--interactive`)
- Full validation summary display
- Confirmation prompts
- Progress indicators with status messages
- Best for troubleshooting or first-time setup

### Verbose Mode (`--verbose`)
- Debug-level logging to console and file
- Detailed operation information
- Shows table operations, file copies, etc.
- Best for debugging issues

## Template File Handling

### How Template Filenames Work

MAESTRO and TOAST use a dynamic template filename system that allows different template files for division vs non-division tournaments:

1. **Season Config (qualifiers.json / championship.json)**:
   - In the `copy_file_list_divisions_only` and `copy_file_list_no_divisions_only` arrays, add a `"type"` field to template files:
     ```json
     {
       "type": "script_template",
       "source": "champ_script_template-with-divisions.html.jinja",
       "dest": "champ_script_template.html.jinja"
     }
     ```
   - Valid type values: `"script_template"`, `"summary_template"`, `"fillin_template"`

2. **MAESTRO Processing**:
   - Reads the copy file lists and extracts entries with a `"type"` field
   - Writes the destination filename to `tournament_config.json` INFO section
   - Example: `"script_template": "champ_script_template.html.jinja"`

3. **TOAST Processing**:
   - Reads template filenames from `tournament_config.json` INFO section
   - **Fallback behavior**: If keys are missing, defaults to:
     - `script_template.html.jinja` for ceremony scripts
     - `summary_template.html.jinja` for ceremony summaries
   - This ensures backward compatibility and graceful degradation

### Example Flow

```
championship.json (divisions_only):
  {"type": "script_template", "source": "champ_script-div.html.jinja", "dest": "champ_script.html.jinja"}
          ↓ MAESTRO copies file and writes config
tournament_config.json (INFO):
  "script_template": "champ_script.html.jinja"
          ↓ TOAST reads config
Uses: champ_script.html.jinja (or falls back to script_template.html.jinja if not found)
```
